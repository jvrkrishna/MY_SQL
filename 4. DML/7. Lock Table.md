# 🔐 Locks in MySQL

In MySQL, **locks** are used to control access to data when multiple users or sessions are working with the database at the same time.

Locks help to:

- Prevent conflicting operations
- Maintain data consistency
- Control concurrent access
- Protect data while a transaction is in progress

MySQL supports different types of locks depending on the storage engine and operation.

The important types of locks are:

1. Table-Level Locks
2. Row-Level Locks
3. Record Locks
4. Metadata Locks
5. Advisory Locks

---

# 1. Connection ID

When working with multiple MySQL sessions, it is useful to identify each connection.

## Syntax

    SELECT CONNECTION_ID();

## Practical Example

Open MySQL and execute:

    SELECT CONNECTION_ID();

Example output:

    +-----------------+
    | CONNECTION_ID() |
    +-----------------+
    | 10              |
    +-----------------+

The connection ID helps us identify the current MySQL session.

This is especially useful when demonstrating locks using two different sessions.

---

# 2. Table-Level Locks

A **Table-Level Lock** locks the complete table.

When a table is locked, the lock applies to the entire table rather than individual rows.

Table-level locking is commonly associated with storage engines such as:

- MyISAM
- MEMORY

The `LOCK TABLES` statement can be used to explicitly lock tables.

There are two commonly used table locks:

1. READ Lock
2. WRITE Lock

---

# 3. READ Lock

A **READ lock** allows the table to be read but prevents modifications while the lock is held.

## Syntax

    LOCK TABLES table_name READ;

## Practical Example

Create a database:

    CREATE DATABASE employee;

Select the database:

    USE employee;

Create a table:

    CREATE TABLE emp_info (
        id INT PRIMARY KEY,
        name VARCHAR(50),
        salary FLOAT
    );

Insert some records:

    INSERT INTO emp_info VALUES
    (1, 'Ram', 30000),
    (2, 'Ravi', 35000),
    (3, 'Rani', 40000);

View the records:

    SELECT * FROM emp_info;

Now apply a READ lock:

    LOCK TABLES emp_info READ;

Read the data:

    SELECT * FROM emp_info;

The SELECT operation is allowed.

Now try to insert a new record:

    INSERT INTO emp_info
    VALUES (4, 'Raju', 45000);

The write operation cannot proceed while the table is held with a READ lock.

Release the lock:

    UNLOCK TABLES;

Now insert the record:

    INSERT INTO emp_info
    VALUES (4, 'Raju', 45000);

Check the table:

    SELECT * FROM emp_info;

---

# 4. READ Lock Using Two Sessions

A better way to understand table locks is by using two MySQL sessions.

Suppose:

    Session 1 -> Connection ID 10
    Session 2 -> Connection ID 11

## Session 1

Check the connection:

    SELECT CONNECTION_ID();

Apply READ lock:

    LOCK TABLES emp_info READ;

Read the data:

    SELECT * FROM emp_info;

Session 1 can read the table.

## Session 2

Check the connection:

    SELECT CONNECTION_ID();

Try to read:

    SELECT * FROM emp_info;

Another session can read the table.

Now try to insert:

    INSERT INTO emp_info
    VALUES (5, 'Raghu', 50000);

The write operation will wait/block while Session 1 continues to hold the READ lock.

## Session 1

Release the lock:

    UNLOCK TABLES;

After the lock is released, Session 2 can continue.

---

# 5. WRITE Lock

A **WRITE lock** gives exclusive access to the table for the session holding the lock.

## Syntax

    LOCK TABLES table_name WRITE;

## Practical Example

Select the database:

    USE employee;

Apply a WRITE lock:

    LOCK TABLES emp_info WRITE;

Read the table:

    SELECT * FROM emp_info;

The current session can read the table.

Insert a record:

    INSERT INTO emp_info
    VALUES (5, 'Raghu', 50000);

The current session can also modify the table.

Update a record:

    UPDATE emp_info
    SET salary = 55000
    WHERE id = 5;

Delete a record:

    DELETE FROM emp_info
    WHERE id = 5;

Release the lock:

    UNLOCK TABLES;

---

# 6. WRITE Lock Using Two Sessions

## Session 1

Check the connection ID:

    SELECT CONNECTION_ID();

Apply WRITE lock:

    LOCK TABLES emp_info WRITE;

Now Session 1 has exclusive access to the table.

## Session 2

Try to read the table:

    SELECT * FROM emp_info;

The operation will wait while Session 1 holds the WRITE lock.

Try to insert:

    INSERT INTO emp_info
    VALUES (6, 'Kiran', 60000);

This will also wait.

## Session 1

Release the lock:

    UNLOCK TABLES;

After the lock is released, Session 2 can continue.

---

# 7. READ Lock vs WRITE Lock

| Feature | READ Lock | WRITE Lock |
|---|---|---|
| Current session can read | Yes | Yes |
| Current session can write | No | Yes |
| Other sessions can read | Yes | No |
| Other sessions can write | No | No |
| Lock scope | Complete table | Complete table |

---

# 8. Row-Level Locks

A **Row-Level Lock** locks specific rows instead of the entire table.

Row-level locking is mainly used by the **InnoDB** storage engine.

Row-level locks are useful when many users are working with different records at the same time.

For example, suppose a table contains:

    ID  NAME   SALARY
    1   Ram    30000
    2   Ravi   35000
    3   Rani   40000

If one transaction locks the row with `ID = 1`, another transaction can still work with rows such as `ID = 2` or `ID = 3`.

---

# 9. Practical Example of Row-Level Lock

Create an InnoDB table:

    CREATE TABLE employee_info (
        id INT PRIMARY KEY,
        name VARCHAR(50),
        salary FLOAT
    ) ENGINE = InnoDB;

Insert data:

    INSERT INTO employee_info VALUES
    (1, 'Ram', 30000),
    (2, 'Ravi', 35000),
    (3, 'Rani', 40000);

Check the data:

    SELECT * FROM employee_info;

---

# 10. FOR UPDATE

`FOR UPDATE` is used inside a transaction to lock the selected rows for updating.

## Syntax

    START TRANSACTION;

    SELECT *
    FROM table_name
    WHERE condition
    FOR UPDATE;

## Practical Example

Start a transaction:

    START TRANSACTION;

Select and lock the row:

    SELECT *
    FROM employee_info
    WHERE id = 1
    FOR UPDATE;

The row with `id = 1` is locked for the current transaction.

Now update the row:

    UPDATE employee_info
    SET salary = 50000
    WHERE id = 1;

Check the data:

    SELECT * FROM employee_info;

Save the changes:

    COMMIT;

The transaction is completed and the lock is released.

---

# 11. FOR UPDATE Using Two Sessions

This example demonstrates row-level locking more clearly.

Suppose we have:

    ID  NAME   SALARY
    1   Ram    30000
    2   Ravi   35000

## Session 1

Start a transaction:

    START TRANSACTION;

Lock the row with ID 1:

    SELECT *
    FROM employee_info
    WHERE id = 1
    FOR UPDATE;

Now Session 1 has locked the row with ID 1.

## Session 2

Try to update the same row:

    START TRANSACTION;

    UPDATE employee_info
    SET salary = 60000
    WHERE id = 1;

The UPDATE may wait because Session 1 currently holds the row lock.

Session 2 is waiting for Session 1 to finish.

## Session 1

Finish the transaction:

    COMMIT;

The lock is released.

Session 2 can now continue its operation.

---

# 12. Row-Level Lock on Different Rows

Row-level locking allows different sessions to work on different rows.

## Session 1

    START TRANSACTION;

    SELECT *
    FROM employee_info
    WHERE id = 1
    FOR UPDATE;

Session 1 locks row `ID = 1`.

## Session 2

    START TRANSACTION;

    UPDATE employee_info
    SET salary = 45000
    WHERE id = 2;

Session 2 can update row `ID = 2` because Session 1 has locked a different row.

Session 1:

    COMMIT;

Session 2:

    COMMIT;

This is one of the important advantages of row-level locking.

---

# 13. FOR SHARE

`FOR SHARE` is used to request a shared lock on selected rows.

It is useful when a transaction needs to read rows while preventing conflicting updates to those rows during the transaction.

## Syntax

    START TRANSACTION;

    SELECT *
    FROM table_name
    WHERE condition
    FOR SHARE;

## Practical Example

Start a transaction:

    START TRANSACTION;

Read the row with a shared lock:

    SELECT *
    FROM employee_info
    WHERE id = 2
    FOR SHARE;

The selected row is read under a shared lock.

Finish the transaction:

    COMMIT;

---

# 14. LOCK IN SHARE MODE

Older MySQL examples commonly use:

    SELECT *
    FROM employee_info
    WHERE id = 2
    LOCK IN SHARE MODE;

In current MySQL versions, `FOR SHARE` is the preferred syntax.

Equivalent modern form:

    SELECT *
    FROM employee_info
    WHERE id = 2
    FOR SHARE;

---

# 15. FOR UPDATE vs FOR SHARE

| Feature | FOR UPDATE | FOR SHARE |
|---|---|---|
| Purpose | Lock rows for update | Lock rows for shared reading |
| Used inside transaction | Yes | Yes |
| Typical operation | UPDATE / DELETE | Consistent reading |
| Example | `SELECT ... FOR UPDATE` | `SELECT ... FOR SHARE` |

---

# 16. Record Locks

A **Record Lock** is an InnoDB lock on an individual index record.

Record locks are part of InnoDB's internal row-locking mechanism.

When a query searches using an index and locks a matching record, InnoDB can place a record lock on that index entry.

## Practical Example

Create a table with a primary key:

    CREATE TABLE employee_record (
        id INT PRIMARY KEY,
        name VARCHAR(50),
        salary FLOAT
    ) ENGINE = InnoDB;

Insert data:

    INSERT INTO employee_record VALUES
    (1, 'Ram', 30000),
    (2, 'Ravi', 35000),
    (3, 'Rani', 40000);

Start a transaction:

    START TRANSACTION;

Lock a specific record:

    SELECT *
    FROM employee_record
    WHERE id = 2
    FOR UPDATE;

Here, InnoDB can lock the indexed record associated with `id = 2`.

Update the record:

    UPDATE employee_record
    SET salary = 45000
    WHERE id = 2;

Complete the transaction:

    COMMIT;

---

# 17. Metadata Locks

A **Metadata Lock (MDL)** protects the metadata or structure of database objects.

MySQL automatically uses metadata locks when tables and other database objects are accessed or modified.

Metadata locks help prevent conflicts between:

- Queries using a table
- ALTER operations
- DROP operations
- RENAME operations
- Other structural changes

---

# 18. Practical Example of Metadata Lock

Create a table:

    CREATE TABLE customer (
        id INT PRIMARY KEY,
        name VARCHAR(50)
    );

Insert data:

    INSERT INTO customer VALUES
    (1, 'Ram'),
    (2, 'Ravi');

---

## Session 1

Start a transaction:

    START TRANSACTION;

Read the table:

    SELECT *
    FROM customer;

Keep the transaction open.

Do not execute `COMMIT` yet.

---

## Session 2

Try to modify the table structure:

    ALTER TABLE customer
    ADD COLUMN age INT;

The `ALTER TABLE` statement may have to wait for the metadata lock held by the first session.

---

## Session 1

Finish the transaction:

    COMMIT;

Now Session 2 can continue with the `ALTER TABLE` operation.

---

# 19. Why Metadata Locks Are Important

Suppose:

    Session 1
        |
        | SELECT
        ↓
    customer table
        |
        | Metadata lock
        ↓
    Session 2
        |
        | ALTER TABLE
        ↓
    Must wait

This prevents MySQL from changing the table structure while another operation is still using the table.

---

# 20. Check Metadata Locks

MySQL Performance Schema can be used to inspect metadata locks.

## Query

    SELECT *
    FROM performance_schema.metadata_locks;

The amount of information available depends on the MySQL version and Performance Schema configuration.

# 21. Deadlock

A **deadlock** occurs when two transactions are waiting for locks held by each other.

Example:

    Transaction 1
        locks Row 1
        waits for Row 2

    Transaction 2
        locks Row 2
        waits for Row 1

Both transactions are waiting for each other.

---

# 22. Practical Example of Deadlock

Create a table:

    CREATE TABLE accounts (
        id INT PRIMARY KEY,
        name VARCHAR(50),
        balance INT
    ) ENGINE = InnoDB;

Insert data:

    INSERT INTO accounts VALUES
    (1, 'Ram', 10000),
    (2, 'Ravi', 15000);

---

## Session 1

Start transaction:

    START TRANSACTION;

Update Account 1:

    UPDATE accounts
    SET balance = balance - 1000
    WHERE id = 1;

Now Session 1 holds a lock related to Account 1.

---

## Session 2

Start transaction:

    START TRANSACTION;

Update Account 2:

    UPDATE accounts
    SET balance = balance - 1000
    WHERE id = 2;

Now Session 2 holds a lock related to Account 2.

---

## Session 1

Now try to update Account 2:

    UPDATE accounts
    SET balance = balance + 1000
    WHERE id = 2;

Session 1 may have to wait for Session 2.

---

## Session 2

Now try to update Account 1:

    UPDATE accounts
    SET balance = balance + 1000
    WHERE id = 1;

Now Session 2 may have to wait for Session 1.

The situation becomes:

    Session 1 → waiting for Session 2

    Session 2 → waiting for Session 1

This is a **deadlock**.

InnoDB detects deadlocks and normally rolls back one of the transactions so that the other transaction can continue.

---

# 23. How to Reduce Deadlocks

A common way to reduce deadlocks is to access rows in a consistent order.

For example, if transactions need to update rows 1 and 2, always update:

    Row 1 → Row 2

instead of allowing some transactions to use:

    Row 1 → Row 2

and others:

    Row 2 → Row 1

Consistent ordering can reduce the possibility of deadlocks.

---

# 24. Advisory Locks

An **Advisory Lock** is a user-defined lock used by an application to coordinate work between different MySQL sessions.

Advisory locks are not automatically associated with a particular table row.

MySQL provides:

    GET_LOCK()

to acquire an advisory lock.

MySQL provides:

    RELEASE_LOCK()

to release the advisory lock.

---

# 25. GET_LOCK()

## Syntax

    SELECT GET_LOCK('lock_name', timeout);

The lock name is a string defined by the application.

The timeout specifies how long MySQL should wait to obtain the lock.

## Return Values

    1     -> Lock acquired

    0     -> Lock not acquired within timeout

    NULL  -> Error

---

# 26. Practical Example of GET_LOCK()

Create a table:

    CREATE TABLE salary_info (
        id INT PRIMARY KEY,
        name VARCHAR(50),
        salary FLOAT
    );

Insert data:

    INSERT INTO salary_info VALUES
    (1, 'Ram', 25000),
    (2, 'Ravi', 30000);

---

## Session 1

Acquire the advisory lock:

    SELECT GET_LOCK('salary_update', 10);

Output:

    1

The lock has been acquired.

Now update the salary:

    UPDATE salary_info
    SET salary = salary + 1000
    WHERE id = 1;

---

# 27. Session 2

Session 2 tries to acquire the same lock:

    SELECT GET_LOCK('salary_update', 5);

If Session 1 is still holding the lock, Session 2 waits for up to 5 seconds.

If the lock is not released during that time, the result can be:

    0

This allows the application to prevent two sessions from performing the same protected operation simultaneously.

---

# 28. RELEASE_LOCK()

## Syntax

    SELECT RELEASE_LOCK('lock_name');

## Practical Example

After Session 1 finishes the salary update:

    SELECT RELEASE_LOCK('salary_update');

Output:

    1

The advisory lock has been released.

---

# 29. Session 2 Acquires the Lock

After Session 1 releases the lock, Session 2 can try again:

    SELECT GET_LOCK('salary_update', 5);

Output:

    1

Now Session 2 owns the advisory lock.

It can perform its operation:

    UPDATE salary_info
    SET salary = salary + 500
    WHERE id = 2;

After finishing:

    SELECT RELEASE_LOCK('salary_update');

---

# 30. Complete Advisory Lock Practical

## Session 1

    SELECT CONNECTION_ID();

    SELECT GET_LOCK('emp_salary_update', 5);

    UPDATE salary_info
    SET salary = salary + 1000
    WHERE id = 1;

    SELECT RELEASE_LOCK('emp_salary_update');

---

## Session 2

    SELECT CONNECTION_ID();

    SELECT GET_LOCK('emp_salary_update', 5);

    UPDATE salary_info
    SET salary = salary + 500
    WHERE id = 2;

    SELECT RELEASE_LOCK('emp_salary_update');

---

# 31. Final Data

Check the table:

    SELECT *
    FROM salary_info;

Expected result:

    +----+------+--------+
    | id | name | salary |
    +----+------+--------+
    |  1 | Ram  |  26000 |
    |  2 | Ravi |  30500 |
    +----+------+--------+

# 32. Multiple Table Locks

The `LOCK TABLES` statement can lock multiple tables in one statement.

## Syntax

    LOCK TABLES
        table1 READ,
        table2 WRITE;

## Practical Example

Create two tables:

    CREATE TABLE orders (
        order_id INT PRIMARY KEY,
        customer_name VARCHAR(50)
    );

    CREATE TABLE products (
        product_id INT PRIMARY KEY,
        product_name VARCHAR(50)
    );

Now lock them:

    LOCK TABLES
        orders READ,
        products WRITE;

Here:

`orders READ`

allows reading but prevents writing.

`products WRITE`

allows the current session to read and write, while other sessions are blocked from accessing the table.

Release the locks:

    UNLOCK TABLES;

---

# 33. Lock Granularity

**Lock Granularity** means the size or level at which a lock is applied.

There are three important levels to understand:

### Row-Level

Locks individual rows.

Example:

    SELECT *
    FROM employee_info
    WHERE id = 1
    FOR UPDATE;

### Table-Level

Locks the entire table.

Example:

    LOCK TABLES emp_info WRITE;

### Metadata-Level

Protects database object structure and metadata.

Example:

    ALTER TABLE emp_info
    ADD COLUMN age INT;

---

# 34. Table-Level Lock vs Row-Level Lock

| Feature | Table-Level Lock | Row-Level Lock |
|---|---|---|
| Lock applies to | Entire table | Selected rows |
| Granularity | Coarse | Fine |
| Concurrency | Lower | Higher |
| Common InnoDB operation | Not the normal row-locking mechanism | Yes |
| Example | `LOCK TABLES` | `FOR UPDATE` |
| Useful for | Explicit table access control | Concurrent transactions |

---

# 35. Row-Level Lock vs Metadata Lock

| Feature | Row-Level Lock | Metadata Lock |
|---|---|---|
| Protects | Table data rows | Table/object metadata |
| Purpose | Prevent conflicting data changes | Prevent conflicting structural changes |
| Example | `SELECT ... FOR UPDATE` | `ALTER TABLE` waiting |
| Automatically used | By InnoDB during many operations | By MySQL server |
| Related to | Transactions and data | DDL and object structure |

---
