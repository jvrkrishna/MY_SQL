# 🔐 Locks in MySQL

In MySQL, **locks** are used to control concurrent access to database objects such as tables and rows.

When multiple users or applications access the same data at the same time, locks help prevent conflicts and maintain **data consistency**.

MySQL provides different types of locks depending on the storage engine, operation, and requirement.

---

# 1. Connection ID

When working with multiple MySQL sessions, it is useful to identify each connection.

### Syntax

    SELECT CONNECTION_ID();

### Example

    SELECT CONNECTION_ID();

This returns the unique connection ID of the current MySQL session.

This is especially useful when demonstrating locks using multiple sessions.

---

# 2. Types of Locks in MySQL

The commonly discussed locks are:

1. Table-Level Locks
2. Row-Level Locks
3. Record Locks
4. Metadata Locks
5. Advisory Locks

---

# 3. Table-Level Locks

A **table-level lock** locks the entire table.

It applies to the complete table rather than individual rows.

Table-level locking is commonly associated with storage engines such as:

- MyISAM
- MEMORY

The InnoDB storage engine primarily uses row-level locking for normal data operations.

---

## 3.1 READ Lock

A `READ` lock allows sessions to read the table but prevents modifications while the lock is held.

### Syntax

    LOCK TABLES table_name READ;

### Example

    LOCK TABLES emp_info READ;

While the table is read-locked:

- The table can be read.
- Other sessions cannot modify the table.
- The lock must be released before normal access can continue.

### Release the Lock

    UNLOCK TABLES;

---

## 3.2 WRITE Lock

A `WRITE` lock provides exclusive access to the table for the locking session.

### Syntax

    LOCK TABLES table_name WRITE;

### Example

    LOCK TABLES emp_info WRITE;

While the table is write-locked:

- The current session can read and modify the table.
- Other sessions cannot read or modify the table until the lock is released.

### Release the Lock

    UNLOCK TABLES;

---

# 4. READ Lock vs WRITE Lock

| Lock Type | Current Session | Other Sessions |
|---|---|---|
| READ | Can read | Can read, cannot write |
| WRITE | Can read and write | Cannot read or write |

---

# 5. Row-Level Locks

A **row-level lock** locks individual rows instead of the entire table.

Row-level locking is an important feature of the **InnoDB** storage engine.

It is useful in systems where many users need to work with different rows at the same time.

### Advantages

- Better concurrency
- Less contention
- Different sessions can work with different rows simultaneously
- Useful for transaction-based applications

Row locks are generally held as part of transactions.

---

# 6. FOR UPDATE

`SELECT ... FOR UPDATE` is used inside a transaction when we want to lock the selected rows for updating.

### Syntax

    START TRANSACTION;

    SELECT *
    FROM table_name
    WHERE condition
    FOR UPDATE;

---

## Example

    START TRANSACTION;

    SELECT *
    FROM emp_info
    WHERE id = 1
    FOR UPDATE;

The selected row is locked for the current transaction.

Another transaction trying to update the same row may have to wait until the first transaction finishes.

### Update the Row

    UPDATE emp_info
    SET salary = 60000
    WHERE id = 1;

### Save the Transaction

    COMMIT;

The lock is released when the transaction ends.

---

# 7. Understanding FOR UPDATE

Consider:

    START TRANSACTION;

    SELECT *
    FROM emp_info
    WHERE id = 1
    FOR UPDATE;

The process is:

    START TRANSACTION
            ↓
    Find the required row
            ↓
    Lock the selected row
            ↓
    Perform UPDATE / DELETE if required
            ↓
    COMMIT or ROLLBACK
            ↓
    Lock is released

---

# 8. Shared Row Lock

A shared lock can be used when a transaction wants to read a row while preventing other transactions from modifying that row in conflicting ways.

In older MySQL syntax, this can be written as:

    START TRANSACTION;

    SELECT *
    FROM emp_info
    WHERE id = 2
    LOCK IN SHARE MODE;

    COMMIT;

In current MySQL versions, the preferred syntax is:

    START TRANSACTION;

    SELECT *
    FROM emp_info
    WHERE id = 2
    FOR SHARE;

    COMMIT;

`FOR SHARE` requests a shared lock on the selected rows.

---

# 9. FOR UPDATE vs FOR SHARE

| Feature | FOR UPDATE | FOR SHARE |
|---|---|---|
| Purpose | Lock rows for modification | Lock rows for shared reading |
| Typical use | Before UPDATE or DELETE | Before reading consistently |
| Transaction required | Yes | Yes |
| InnoDB | Yes | Yes |

---

# 10. Record Locks

A **record lock** is an InnoDB lock on an individual index record.

Record locks work at a lower level as part of InnoDB's row-locking mechanism.

For example:

    SELECT *
    FROM emp_info
    WHERE id = 5
    FOR UPDATE;

If `id` is indexed, InnoDB can lock the relevant index record.

Record locks help prevent conflicting modifications to specific records.

---

# 11. Metadata Locks (MDL)

**Metadata Locks**, commonly called **MDL**, protect the structure or metadata of database objects.

MySQL automatically acquires metadata locks when tables and other objects are accessed.

Metadata locks are important because MySQL must prevent structural changes from conflicting with operations that are currently using an object.

---

# 12. Why Metadata Locks Exist

Suppose one session is using a table:

    SELECT *
    FROM emp_info;

At the same time, another session wants to change the table:

    ALTER TABLE emp_info
    ADD COLUMN age INT;

MySQL must coordinate these operations so that the table is not structurally changed while another operation is using its metadata.

Therefore, the `ALTER TABLE` operation may have to wait.

---

# 13. Metadata Lock Example

### Session 1

    START TRANSACTION;

    SELECT *
    FROM emp_info;

If the transaction continues to hold the relevant metadata lock, another session may have to wait for the transaction to finish.

### Session 2

    ALTER TABLE emp_info
    ADD COLUMN email VARCHAR(100);

The `ALTER TABLE` statement may wait until the blocking transaction releases its metadata lock.

### Session 1

    COMMIT;

After the blocking transaction finishes, Session 2 may continue.

---

# 14. When Metadata Locks Are Used

Metadata locks can be involved when:

- A table is queried
- A table is modified
- A table structure is changed
- A table is renamed
- A table is dropped
- Other database object definitions are accessed or changed

Metadata locks are generally acquired automatically by MySQL.

---

# 15. Common Metadata Lock Problem

A common situation is:

    Session 1
        ↓
    Long-running transaction
        ↓
    Table is being used
        ↓
    Metadata lock remains

Then:

    Session 2
        ↓
    ALTER TABLE
        ↓
    ALTER waits

This can make an `ALTER TABLE` or similar DDL statement appear to be hanging.

---

# 16. Checking Metadata Locks

Metadata lock information can be inspected using Performance Schema.

### Query

    SELECT *
    FROM performance_schema.metadata_locks;

The availability and amount of information depend on the MySQL version and Performance Schema configuration.

---

# 17. Deadlock

A **deadlock** occurs when two or more transactions are waiting for each other's locks.

For example:

    Transaction A
        locks Row 1
        waits for Row 2

    Transaction B
        locks Row 2
        waits for Row 1

Now:

    A → waiting for B
    B → waiting for A

Neither transaction can continue without intervention.

---

# 18. Deadlock Example

### Transaction 1

    START TRANSACTION;

    UPDATE emp_info
    SET salary = 50000
    WHERE id = 1;

Now Transaction 1 has a lock related to row `id = 1`.

### Transaction 2

    START TRANSACTION;

    UPDATE emp_info
    SET salary = 60000
    WHERE id = 2;

Now Transaction 2 has a lock related to row `id = 2`.

If Transaction 1 then tries:

    UPDATE emp_info
    SET salary = 55000
    WHERE id = 2;

and Transaction 2 tries:

    UPDATE emp_info
    SET salary = 65000
    WHERE id = 1;

they can end up waiting for each other.

InnoDB detects deadlocks and normally rolls back one of the transactions so that the other can continue.

---

# 19. Lock Granularity

**Lock granularity** means the size or level at which a lock is applied.

Common levels include:

### Row-Level

Locks individual rows.

    Fine-grained

Provides high concurrency.

### Table-Level

Locks the entire table.

    Coarse-grained

Can reduce concurrency because the complete table is locked.

### Metadata-Level

Protects the metadata or structure of database objects.

# 22. Practical: Table READ Lock

### Step 1: Check Connection ID

    SELECT CONNECTION_ID();

### Step 2: Acquire READ Lock

    LOCK TABLES emp_info READ;

Now the table is locked for reading by the current session.

### Step 3: Read the Data

    SELECT *
    FROM emp_info;

Reading is allowed.

### Step 4: Try to Insert

    INSERT INTO emp_info
    VALUES (4, 'Raju', 'KKD', 45000);

A write operation cannot be performed while the table is held under a READ lock by the session.

### Step 5: Release the Lock

    UNLOCK TABLES;

---

# 23. Practical: Table WRITE Lock

### Acquire WRITE Lock

    LOCK TABLES emp_info WRITE;

The current session has exclusive table access.

### Read Data

    SELECT *
    FROM emp_info;

### Insert Data

    INSERT INTO emp_info
    VALUES (4, 'Raju', 'KKD', 45000);

### Release the Lock

    UNLOCK TABLES;

Other sessions may have to wait while the WRITE lock is held.

# 24. Practical: Row-Level Lock with FOR UPDATE

First start a transaction:

    START TRANSACTION;

Then lock the required row:

    SELECT *
    FROM emp_info
    WHERE id = 1
    FOR UPDATE;

Only the selected row is locked for the transaction, rather than explicitly locking the complete table.

Now update the row:

    UPDATE emp_info
    SET salary = 60000
    WHERE id = 1;

Finish the transaction:

    COMMIT;

    FOR SHARE;

### Finish Transaction

    COMMIT;

`FOR SHARE` requests a shared lock on the selected rows.

# 26. Advisory Locks

An **advisory lock** is a user-defined, application-level lock.

Unlike normal row or table locks, an advisory lock is not automatically associated with a particular table row.

Advisory locks are useful when an application needs to coordinate work between multiple sessions.

MySQL provides:

    GET_LOCK()

to acquire a named advisory lock.

And:

    RELEASE_LOCK()

to release it.

---

# 27. GET_LOCK()

### Syntax

    SELECT GET_LOCK('lock_name', timeout);

Example:

    SELECT GET_LOCK('my_custom_lock', 10);

Here:

    'my_custom_lock'
    
is the name of the advisory lock.

    10

is the maximum time, in seconds, to wait for the lock.

### Return Values

    1     -> Lock acquired

    0     -> Lock was not acquired within the timeout

    NULL  -> Error occurred

---

# 28. RELEASE_LOCK()

### Syntax

    SELECT RELEASE_LOCK('lock_name');

### Example

    SELECT RELEASE_LOCK('my_custom_lock');

Possible results:

    1     -> Lock was released

    0     -> Lock was not held by the current session

    NULL  -> Lock does not exist or an error occurred

---

# 29. Advisory Lock Practical Example

### Step 1: Create Table

    CREATE TABLE EMP_INFO (
        ID INT PRIMARY KEY,
        FIRST_NAME VARCHAR(50),
        LAST_NAME VARCHAR(50),
        SALARY FLOAT
    );

---

# 30. Insert Data

    INSERT INTO EMP_INFO
    (ID, FIRST_NAME, LAST_NAME, SALARY)
    VALUES
    (1, 'Ram', 'Kumar', 25000),
    (2, 'Ravi', 'Sharma', 30000);

Check the data:

    SELECT *
    FROM EMP_INFO;

---

# 31. Advisory Lock - Session 1

Session 1 acquires the lock:

    SELECT GET_LOCK('emp_salary_update', 5);

Output:

    1

The lock has been acquired.

Now perform the protected operation:

    UPDATE EMP_INFO
    SET SALARY = SALARY + 1000
    WHERE ID = 1;

---

# 32. Advisory Lock - Session 2

At the same time, Session 2 tries to acquire the same advisory lock:

    SELECT GET_LOCK('emp_salary_update', 5);

If Session 1 still holds the lock and Session 2 cannot obtain it within 5 seconds, the result will be:

    0

Session 2 should wait or handle the failure according to the application's logic.

---

# 33. Release Advisory Lock - Session 1

After completing the operation:

    SELECT RELEASE_LOCK('emp_salary_update');

Output:

    1

The advisory lock is released.

---

# 34. Session 2 Acquires the Lock

After Session 1 releases the lock, Session 2 can try again:

    SELECT GET_LOCK('emp_salary_update', 5);

Output:

    1

Now Session 2 owns the advisory lock.

It can perform its operation:

    UPDATE EMP_INFO
    SET SALARY = SALARY + 500
    WHERE ID = 2;

Then release the lock:

    SELECT RELEASE_LOCK('emp_salary_update');

---

# 35. Final Result

    SELECT *
    FROM EMP_INFO;

Expected result:

    +----+------------+-----------+--------+
    | ID | FIRST_NAME | LAST_NAME | SALARY |
    +----+------------+-----------+--------+
    | 1  | Ram        | Kumar     | 26000  |
    | 2  | Ravi       | Sharma    | 30500  |
    +----+------------+-----------+--------+

# 36. Mixed Table Lock Example

MySQL can lock multiple tables using one `LOCK TABLES` statement.

Example:

    LOCK TABLES
        orders READ,
        products WRITE;

Here:

`orders READ`

- Other sessions can read `orders`.
- Other sessions cannot write to `orders`.

`products WRITE`

- The current session can read and write `products`.
- Other sessions cannot read or write `products` while the lock is held.

Release all explicit table locks:

    UNLOCK TABLES;

---

# 37. Table Locks vs Row Locks

| Feature | Table-Level Lock | Row-Level Lock |
|---|---|---|
| Lock scope | Entire table | Selected rows |
| Granularity | Coarse | Fine |
| Concurrency | Lower | Higher |
| Commonly associated with | MyISAM, MEMORY | InnoDB |
| Typical use | Explicit table locking | Transactions |
| Example | `LOCK TABLES` | `FOR UPDATE` |

---

# 38. Row Locks vs Metadata Locks

| Feature | Row Lock | Metadata Lock |
|---|---|---|
| Protects | Data rows | Object metadata/structure |
| Commonly associated with | InnoDB | MySQL server |
| Example | `SELECT ... FOR UPDATE` | `ALTER TABLE` waiting for active use |
| Purpose | Prevent conflicting data changes | Prevent conflicting structural changes |
