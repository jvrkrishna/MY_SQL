# SQL VIEW

## 1. What is a View?

A **View** is a **virtual table** created from one or more existing tables using a SQL query.

A view does not normally store the actual table data separately. Instead, it stores the **SQL query definition**, and when we query the view, the database retrieves the required data from the underlying (base) table(s).

### Simple Definition

> A View is a virtual table based on the result of a SQL `SELECT` query.

A view can be created from:

* One table
* Multiple tables
* Joins
* Selected columns
* Selected rows
* Aggregate queries, depending on the database and query

---

# 2. How a View Works

Suppose we have this table:

```sql
EMP_INFO
------------------------------------------------
ID     NAME      DEPT       SALARY
101    Ravi      HR         45000
102    Anita     IT         70000
103    Suman     Finance    85000
104    John      IT         90000
105    Priya     HR         40000
```

We can create a view containing only employees whose salary is greater than `60000`.

```sql
CREATE VIEW high_salary_employees AS
SELECT ID, NAME, SALARY
FROM EMP_INFO
WHERE SALARY > 60000;
```

The view behaves like a table when queried:

```sql
SELECT * FROM high_salary_employees;
```

The result is:

```text
ID     NAME      SALARY
-----  --------  ------
102    Anita     70000
103    Suman     85000
104    John      90000
```

---

# 3. Relationship Between Table and View

The important point is that a view is based on its underlying table(s).

### Changes in the Base Table → View

If data in the base table changes, the change is reflected when we query the view, provided the changed row still satisfies the view's condition.

For example:

```sql
UPDATE EMP_INFO
SET SALARY = 50000
WHERE ID = 102;
```

Previously, Anita had a salary of `70000`, so she appeared in the view.

After changing her salary to `50000`, she no longer satisfies:

```sql
WHERE SALARY > 60000
```

Therefore:

```sql
SELECT * FROM high_salary_employees;
```

will no longer show Anita.

### Important Correction

Do **not** write:

> Changes made in table reflect on view 100%.

A better statement is:

> Changes made to the underlying table are reflected in the view when the view is queried, subject to the view's definition.

For example, if a row no longer satisfies the `WHERE` condition, it may disappear from the view.

---

# 4. Changes in View → Base Table

Some views are **updatable**, meaning we can perform operations such as:

```sql
INSERT
UPDATE
DELETE
```

through the view.

When an update is allowed through an updatable view, the change is made to the underlying base table.

Example:

```sql
UPDATE high_salary_employees
SET SALARY = 75000
WHERE ID = 102;
```

If this view is updatable, the corresponding row in `EMP_INFO` is also updated.

Check the base table:

```sql
SELECT * FROM EMP_INFO
WHERE ID = 102;
```

Result:

```text
ID     NAME      DEPT    SALARY
-----  --------  ------  ------
102    Anita     IT      75000
```

### Important

Not every view is automatically updatable.

Whether a view can be modified depends on:

* The SQL database system
* How the view was created
* Whether it contains joins
* Aggregate functions
* `GROUP BY`
* `DISTINCT`
* Calculated expressions
* Other restrictions imposed by the database

Therefore, the statement:

> Changes made in view reflect on table if columns are same.

is **too broad**.

A better statement is:

> Changes made through an updatable view can modify the underlying base table. Whether a view is updatable depends on the view definition and the database system.

---

# 5. Advantages of Views

## 5.1 Data Security

A view can expose only the required columns and rows to a user.

For example, suppose `EMP_INFO` contains:

```text
ID
NAME
DEPT
SALARY
```

We can create a view that does not expose salary:

```sql
CREATE VIEW employee_public AS
SELECT ID, NAME, DEPT
FROM EMP_INFO;
```

Users can access:

```sql
SELECT * FROM employee_public;
```

without directly seeing the salary column.

> Note: A view is one part of a security design. Proper database privileges/permissions should also be used.

---

## 5.2 Customized Data

Different users can see different subsets of data.

For example:

```sql
CREATE VIEW it_employees AS
SELECT ID, NAME, SALARY
FROM EMP_INFO
WHERE DEPT = 'IT';
```

The HR department could have a different view, while management could have another view.

---

## 5.3 Simplifies Complex Queries

Suppose a query involves multiple tables and joins.

Instead of asking users to repeatedly write the complicated query, we can create a view once:

```sql
CREATE VIEW employee_department_details AS
SELECT ...
FROM ...
JOIN ...;
```

Users can then simply write:

```sql
SELECT * FROM employee_department_details;
```

This makes frequently used queries easier to work with.

---

## 5.4 Reduces Query Complexity

A view can hide the complexity of the underlying query.

Instead of remembering a long query, users can work with the view like a table.

---

## 5.5 Little or No Additional Data Storage

A normal view generally stores the **query definition**, not a separate copy of the underlying data.

Therefore, a normal view usually requires very little additional storage compared with storing another copy of the data.

### Important Correction

Do not say:

> View uses little storage space.

as an absolute rule.

A better statement is:

> A normal view generally requires little additional storage because it stores the view definition rather than a separate copy of the result data.

Some databases also support **materialized views**, which physically store query results and therefore require additional storage.

---

# 6. Disadvantages of Views

## 6.1 Not Every View Is Updatable

Some views cannot be directly modified.

For example, views involving:

* `GROUP BY`
* Aggregate functions such as `SUM()`, `AVG()`, `COUNT()`
* `DISTINCT`
* Complex joins
* Certain calculated expressions

may not be directly updatable, depending on the database system.

---

## 6.2 Performance Can Be Affected

A normal view does not automatically make a query faster.

When the view is queried, the database generally has to execute the underlying query.

A simple view may have little overhead, while a complex view involving several joins or calculations can be expensive.

---

## 6.3 Dependency on Base Tables

A view depends on the underlying table(s).

Changes to the structure of those tables can affect the view.

For example, dropping or renaming a column used by a view may cause the view to become invalid or require modification, depending on the database system.

---

## 6.4 Indexing

The statement:

> Cannot be indexed.

is **not universally correct**.

A better statement is:

> A normal view generally does not have its own indexes because it does not normally store its result as physical data. Some database systems support special forms such as indexed views or materialized views, with database-specific rules.

---

# 7. Syntax

Basic syntax:

```sql
CREATE VIEW view_name AS
SELECT column1, column2, ...
FROM table_name
WHERE condition;
```

Example:

```sql
CREATE VIEW high_salary_employees AS
SELECT ID, NAME, SALARY
FROM EMP_INFO
WHERE SALARY > 60000;
```

# 9. Create a View

Create a view that displays employees whose salary is greater than `60000`.

```sql
CREATE VIEW high_salary_employees AS
SELECT ID, NAME, SALARY
FROM EMP_INFO
WHERE SALARY > 60000;
```

---

# 10. Query the View

```sql
SELECT * FROM high_salary_employees;
```

Expected output:

```text
ID     NAME      SALARY
-----  --------  ------
102    Anita     70000
103    Suman     85000
104    John      90000
```

Notice that:

* Ravi is not shown because his salary is `45000`.
* Priya is not shown because her salary is `40000`.
* Anita, Suman, and John are shown because their salaries are greater than `60000`.

---

# 11. Update Data Through the View

Because this is a simple view based on one table and selected columns, many database systems allow an update through it.

```sql
UPDATE high_salary_employees
SET SALARY = 75000
WHERE ID = 102;
```

Now check the base table:

```sql
SELECT * FROM EMP_INFO
WHERE ID = 102;
```

Expected output:

```text
ID     NAME      DEPT    SALARY
-----  --------  ------  ------
102    Anita     IT      75000
```

The change made through the view has changed the underlying table.

---

# 12. Important Practical Example — Row Can Disappear from the View

This is a very useful example for understanding views.

Suppose we execute:

```sql
UPDATE EMP_INFO
SET SALARY = 50000
WHERE ID = 102;
```

Now Anita's salary is `50000`.

But our view has:

```sql
WHERE SALARY > 60000
```

So run:

```sql
SELECT * FROM high_salary_employees;
```

Anita will no longer appear.

Why?

Because the view does not permanently store the old result. The view is based on the current data in `EMP_INFO`.

Current table:

```text
ID     NAME      DEPT       SALARY
-----  --------  ---------  ------
101    Ravi      HR         45000
102    Anita     IT         50000
103    Suman     Finance    85000
104    John      IT         90000
105    Priya     HR         40000
```

Current view:

```text
ID     NAME      SALARY
-----  --------  ------
103    Suman     85000
104    John      90000
```

Anita disappeared because she no longer satisfies:

```sql
SALARY > 60000
```

This is one of the most important concepts to remember about views.

---

# 13. Drop the View

To remove the view:

```sql
DROP VIEW high_salary_employees;
```

This removes the **view**, not the underlying table.

The `EMP_INFO` table still exists.

```sql
SELECT * FROM EMP_INFO;
```

will still work.

# 14. View vs Table

| Feature                                   | Table                                         | View                             |
| ----------------------------------------- | --------------------------------------------- | -------------------------------- |
| Stores actual data                        | Yes                                           | Normally no                      |
| Physical storage                          | Yes                                           | Normally stores query definition |
| Created using                             | `CREATE TABLE`                                | `CREATE VIEW`                    |
| Can contain selected columns              | Yes                                           | Yes                              |
| Can contain selected rows                 | Yes                                           | Yes                              |
| Can be based on multiple tables           | Data can be related using queries/joins       | Yes                              |
| Automatically reflects base-table changes | N/A                                           | Yes, when queried                |
| Always updatable                          | Generally supports DML subject to constraints | No                               |
| Can normally have its own indexes         | Yes                                           | Normal views generally no        |
| Main purpose                              | Store data                                    | Present/customize data           |

# 15. View vs Materialized View

Do not confuse a normal **View** with a **Materialized View**.

### Normal View

A normal view generally stores the query definition.

```sql
CREATE VIEW high_salary_employees AS
SELECT ID, NAME, SALARY
FROM EMP_INFO
WHERE SALARY > 60000;
```

The data is generally obtained from the underlying table when the view is queried.

### Materialized View

A materialized view stores the query result physically.

Conceptually:

```text
Base Tables
     ↓
Complex Query
     ↓
Materialized View
     ↓
Stored Result
```

Because the result is physically stored, materialized views can sometimes improve performance for expensive queries, but they require storage and must be refreshed to keep the result current.

> Exact materialized-view syntax and behavior depend on the database system.

---

# 16. Key Points for Exams / Interviews

1. A **view is a virtual table**.
2. A view is created using `CREATE VIEW`.
3. A view is generally based on a `SELECT` query.
4. A view can be created from one or more tables.
5. A view can contain selected rows and/or selected columns.
6. A normal view generally does not store a separate copy of the data.
7. Changes in the underlying table can be reflected in the view when the view is queried.
8. Some views are **updatable**, while others are not.
9. Updating an updatable view can update the underlying base table.
10. Views can improve **data security** by exposing only required data.
11. Views can provide a **customized representation** of data.
12. Views can simplify complex queries.
13. A normal view generally does not have its own physical indexes.
14. Some database systems support special indexed/materialized view features.
15. Dropping a view does **not normally delete the underlying table data**.

---

# 17. One-Line Memory Trick

> **TABLE stores the data; VIEW shows the data according to a query.**

```text
                BASE TABLE
                    |
                    | SELECT query
                    ↓
                  VIEW
                    |
                    ↓
              User sees data
```

If the base table changes:

```text
BASE TABLE changes
        ↓
VIEW result can change
```

If an updatable view is modified:

```text
VIEW UPDATE
     ↓
BASE TABLE UPDATE
```

But remember:

> **Not every view is updatable.**
